# Agent Delivery Contract

Use this contract for delegated implementation, review, research, recovery, and external-agent work. It complements runtime liveness: runtime evidence proves an Agent is executing; this contract proves it is executing the right bounded goal and returning auditable evidence.

## 1. Single Goal Assignment

Every delivered Assignment in `ACKED`, `ACTIVE`, or `CANDIDATE` has exactly one `primary_goal` plus:

- `success_criteria`: observable conditions that close the goal.
- `owned_scope`: the bounded files, interfaces, decisions, or evidence the Agent may change or produce.
- `forbidden_scope`: explicit nearby scope the Agent must not absorb. An empty list is allowed when ownership already makes the exclusion obvious.
- `parallelizable`: explicit boolean. `false` requires `dependency_reason`; `true` still remains subject to READY, ownership, and shared-contract gates.

RED, implementation, GREEN, review, and documentation are steps or evidence for one goal, not separate hidden goals. If the primary goal changes, freeze/terminate the current Assignment and issue a new one.

For Assignment-bound external execution, delivered ACK is a **launch gate**, not a retrospective quality check. The runner validates the exact Assignment/task/Agent identity plus repository root, branch, and current HEAD before spawning the external Agent. A useful result produced through a non-compliant launch may remain auxiliary evidence, but it cannot satisfy the required Assignment or Reviewer receipt.

Before any new Assignment becomes launchable, the control receipt freezes its execution mode, unique owned files, and route evidence. Delegated execution must bind the actual provider/model/auth mode to the exact project policy file and SHA, and only active policy declarations with independent provider/model/auth field names count. The route class must be explicitly declared before the first valid route field, and that prefix is parsed with a positive declaration grammar: only the class marker plus optional formal default/fallback directives are accepted; unknown, negative, or exclusion words fail closed. Provider/model values cannot satisfy the class marker. Whole-line or trailing comments, Markdown/HTML fenced or indented code/examples, inline-code declarations, disabled/negative rules (including space, underscore, ASCII hyphen, Unicode dash, and fullwidth-hyphen variants such as must not / must-not / must_not and never forms), and pseudo-fields joined by underscore or any normalized dash do not authorize execution. Route parsing normalizes Unicode compatibility forms and dash equivalents before field-boundary and negation checks. A fallback is launchable only when the new route references a concrete `prior_assignment_id` and canonical Runtime proves that prior Assignment belongs to the same task, the declared `fallback_from` exactly matches its persisted provider/model/auth mode, the prior attempt has a failure terminal with known result, and the route's traceable `failure_evidence` is actually present in that terminal evidence. Caller-authored `prior_attempt_terminal` / `result_unknown` flags are not authorization. Policy validation applies to the selected fallback provider/model/auth route itself. Fresh Assignment-bound external launch additionally requires contract v2 with a canonical route, compares the actual CLI engine/model/auth mode against that route before spawn, and persists the exact route contract into the canonical start lease. Legacy v1 receipts remain readable only to let already-started historical attempts close; they cannot authorize a fresh external provider spawn. Controller-authored implementation is still an Assignment: it requires an explicit bounded exception and stop condition, so omitting delegation cannot silently convert the Controller into a Writer.

## 2. Delivery Gate — Unified Result Envelope

All execution transports (native subagent, Grok/Kimi runner, future A2A transport) keep **transport completion** separate from the **delivery verdict** in the runtime terminal receipt. New terminal receipts use:

Host fallback is part of execution lineage, not a new Assignment identity. When host routing is involved, the dispatch/delivery evidence additionally records `controller_host`, `execution_host`, `host_fallback_level`, and the machine reason for crossing hosts. Moving Web→Desktop or Desktop→Web never resets attempt/recovery budget and never upgrades model tier merely because the host changed.

`task_id + assignment_id + attempt + lease_id + terminal_state + transport_outcome + delivery_outcome + summary + evidence[] + artifacts[] + next_action + retry_class`

`transport_outcome` answers only whether the provider/process completed, failed, was cancelled, or was transport-blocked. `delivery_outcome` is independently `pass | fail | blocked | unresolved`. Provider exit code `0` means transport completed only; without an explicit validated delivery receipt the delivery remains `unresolved`, never PASS. Legacy receipts with one `outcome` remain readable during migration but must not be emitted by new runner writes.

When code or a versioned artifact is produced, Delivery PASS requires explicit evidence and an exact artifact/revision. PASS evidence/artifact entries must be traceable locators rather than free-form prose; the runner and canonical runtime reject prose-only PASS claims. Transport-specific prose may be retained as non-PASS evidence, but prose or exit code alone is not an authoritative delivery result. If a provider process completed but its delivery receipt is unreadable or invalid, runtime still closes the process as `transport_outcome=completed` with `delivery_outcome=unresolved`, while the caller receives a non-zero error for the invalid receipt.

Runtime heartbeat is liveness only. A progress receipt extends the progress deadline only when at least one authoritative fingerprint changes (Git HEAD, tracked status hash, evidence receipt, artifact, or blocker evidence). Repeating the same fingerprint does not count as progress. Same-contract recovery is bounded to two recovery attempts; after exhaustion the same Assignment cannot start another attempt. Strategy-changing execution must use a new Assignment contract rather than silently resetting the counter. Checkpoint governance stays risk-tailored: checkpoint 只作为恢复锚点，ordinary short assignments do not gain a new mandatory approval step or controller-authored runtime field.

For external side effects (for example payment, publish, message send, resource creation, or third-party writes), contract v2 and later Assignment starts explicitly record `side_effect: true|false`; a side-effecting Assignment may also bind one stable `idempotency_key`. The canonical runtime freezes both facts for the Assignment. Canonical runtime receipt application serializes the complete load→apply→save transaction with one Git-common-dir cross-process lock, so concurrent Agent processes cannot overwrite each other’s heartbeat, progress, terminal, or unknown-result evidence. A terminal side-effect receipt must explicitly record whether the external result is unknown. A v2 side-effecting attempt is recorded as `result_unknown=true` from `assignment_started` onward; only a durable terminal receipt that proves the concrete outcome may clear it. Therefore host death, agent death, or failure to persist the terminal receipt cannot silently turn an in-flight side effect into a retryable known result. If the previous result is unknown/ambiguous, the next attempt is rejected by the runtime start gate even when a stable idempotency key was carried in the Assignment, because prompt/environment propagation alone does not prove that the concrete provider/API applied that key at the mutation boundary. Recovery cannot change `side_effect`, the key, or the contract version in place. Pre-v2 receipts already issued before this field existed remain readable as legacy v1 so an in-flight first attempt can close normally; because their side-effect contract is unknown, an in-flight legacy lease is persisted with `result_unknown=true` until a terminal receipt proves its outcome, and any unresolved legacy result requires a new explicit Assignment before recovery. A stable idempotency key is retained and propagated as contract information, but automatic retry remains blocked until a concrete side-effect adapter can machine-prove provider-level idempotency; the key never resets the recovery budget or turns an unknown result into success. Web execution timeout follows the same rule without requiring a Host terminal API: the Runtime-owned `launchd KeepAlive` health-only scheduler periodically reconciles canonical Web leases and structured collaboration events through the existing lifecycle bridge. A `progress_watchdog` lease becomes unhealthy only from lack of authoritative progress beyond its configured deadline/grace; machine `SubAgentActivity completed/failed/interrupted/cancelled/disconnected` may close only the exact bound execution session. Internal Web mutation helpers must re-verify the Host-attested source at the write boundary; an importable/private Python function or caller-supplied observation object is never authorization. The canonical Web lease start time is the reverified machine-observed `started` timestamp on both structured-collaboration and Host-attested paths; the Host verifier must attest that timestamp itself, and neither caller/ingestion time nor later scheduler reconciliation time may become the lease start. Both terminal and unhealthy outcomes feed `terminal_continuation` and the existing same-controller Web reentry supervisor; transient `web_reentry_unavailable` preserves the pending event and re-arms that same supervisor rather than introducing another wake mechanism. `side_effect=false` may enter same-contract recovery, while unknown/legacy side-effect state fails closed. The replacement Web session is bound only after the same logical Controller is woken, and Runtime—not the caller—derives the next attempt and fresh lease under the existing recovery budget. The first durable terminal receipt makes that attempt immutable: no later heartbeat, progress, or second terminal receipt may rewrite the same attempt. A completed/PASS Assignment cannot be reopened as another recovery attempt. For any side-effecting terminal result, including PASS, `result_unknown=false` is accepted only with non-empty structured provider/resource `reconciliation_evidence`. Each evidence item must separately declare the exact runtime `provider`, a non-empty concrete `resource`, a traceable `receipt:` or `artifact:` `locator`, and an `idempotency_key` that exactly equals the Assignment key when one is bound (or is absent when no key exists). Substring/prefix matches, generic file/git evidence, or an executor assertion cannot clear the unknown-result safety latch.

## 3. Integration Gate — Evidence Chain

For implementation work, completion evidence should form the shortest applicable causal chain:

`RED/problem evidence -> exact revision/artifact -> GREEN/verification -> non-author review when required -> real-end acceptance when required -> integration decision`

Every downstream decision cites exact upstream evidence. Skill installation is likewise one cross-process transaction: deterministically ordered locks cover every shared install resource (target Skill, hooks file, and `.zshenv`) across snapshot, exact-revision promotion, host adapter writes, manifest commit, and rollback for both full and core-only installs; installers with different targets still serialize when they share host configuration, and concurrent installers fail closed rather than overwriting or rolling back one another. Runtime upgrades are additionally linear-history only: the candidate Git object database must contain the exact currently installed revision, and that installed revision must be an ancestor of the candidate. A temporary-repository hotfix therefore cannot become an orphan installed truth; it must be imported and absorbed into canonical Runtime history before any later installation can proceed. For the full Web Runtime product, the installer also materializes the exact immutable candidate revision and runs the required release regression set before promotion;  that gate covers same-controller continuation, trusted Web dispatch/terminal provenance with no caller-injected verifier seams, project-wide runnable fairness, derived-runnable promotion, cross-line capacity use, fixed Controller control-loop receipts, generic deviation-to-correction closure, and recurrence escalation, and missing regression files or any failing required case blocks installation. Every downstream decision cites exact upstream evidence. A claim such as “reviewer approved” or “tests passed” without the relevant revision/receipt is insufficient for integration. Required machine review should run through `scripts/reviewer_supervisor.py`: one repository-level active-review lock in Git common-dir prevents concurrent Supervisor runs for the same repository, and it rejects a dirty worktree, captures the exact candidate HEAD and resolves the requested base ref to an immutable commit before launch, runs a dedicated read-only structured `codex exec` Reviewer over exactly that immutable range, revalidates HEAD/status after the attempt, injects the complete structured verdict contract with that exact HEAD and enforces its shape through Codex `--output-schema`, requires observable Codex execution plus a validated terminal verdict, and treats timeout/missing/malformed/stale output as `REVIEW_INFRA_FAILED`; a PID or exit code alone is never review evidence. Native `codex exec review` remains an interactive/manual path rather than the machine-verdict path. Web audit ingestion follows the same evidence rule: one cursor-scoped cross-process consumer lock covers read → `pending` → dispatch → `handled` → cursor advance, cursor progress is committed only after durable successful handling, and atomic state writes use unique temporary files; a crash, failed hook, or concurrent consumer therefore cannot silently discard, duplicate-dispatch, or blindly replay an unknown control event. Each attempt is time-bounded and captures a fixed process-group id at launch; timeout sends SIGTERM to that fixed group, checks descendants even if the leader exits, escalates surviving group members to SIGKILL after the grace period, and permits retry only after both leader reaping and full process-group disappearance are confirmed. Launch failures, broken or blocked stdin delivery, non-timeout wait/reap failures, and process-group signaling failures must all remain inside the same bounded attempt and become durable `REVIEW_INFRA_FAILED` evidence rather than escaping with the run left at `STARTING`; any launched child must undergo verified process-group cleanup, and retry is forbidden whenever safe cleanup cannot be confirmed. In addition to `--output-schema`, the local validator independently accepts exactly the five verdict keys (`reviewed_head`, `verdict`, `critical`, `important`, `minor`) and rejects extras. Infrastructure failure may retry once under the identical immutable review contract, while actual findings are terminal review evidence and are not auto-retried. Once a required Reviewer returns `PASS`, the control event must either complete integration with machine-verified candidate ancestry in the exact current main plus current-main regression evidence or record a real `ordered_integration` queue checkpoint; `FAIL` must return the same candidate to an acknowledged rework Assignment. These are transition evidence, not new lifecycle states.

For bug fixes and high-risk behavior changes (including migration, money/cost, authorization, state-machine, external-call, and release-critical logic), the non-author Reviewer is a **TDD causal-evidence reviewer**. Its review receipt sets `tdd_required=true` and must bind `red_evidence`, exact `candidate_revision`, `green_evidence`, `red_green_same_case=true`, `reviewer_counterexample`, and `verdict=PASS|FAIL`. The Reviewer verifies that the pre-fix RED genuinely exposed the same defect that becomes GREEN on the candidate, and performs a bounded counterexample or edge attack; a test added only after the fix that was never observed failing cannot establish the causal chain. Low-risk mechanical/text changes remain risk-tailored and do not require synthetic RED/GREEN ceremony.

Research-only or diagnostic work uses the analogous chain `question -> source/observation -> finding -> independent check when risk requires -> decision` rather than fabricating RED/GREEN steps.

## 4. Conflict Record

When independent Agents or reviewers reach materially conflicting conclusions about the same revision/decision, do not silently choose one. Record one conflict object containing:

- `conflict_id`, `task_id`, exact revision/decision under dispute;
- each position with its evidence references;
- `arbiter` (controller or explicitly assigned non-author adjudicator);
- `decision`, `decision_evidence`, and resulting `next_action`.

A conflict blocks the disputed integration decision until adjudicated. Code-review defects and design/requirements disputes may share this envelope but remain distinct conflict types.

## 5. Progressive Scale-up

A new provider, model route, or execution transport starts with bounded concurrency. Before raising concurrency, demonstrate one lifecycle covering dispatch/ACK, start, progress or checkpoint, terminal success, and one controlled failure/recovery path. Existing trusted routes do not repeat this ceremony unless the transport/auth/runtime contract materially changes.

Do not build a full A2A server or transactional event bus merely to satisfy this contract. The governance contract is transport-neutral so a future A2A execution layer can replace the current runner without replacing Assignment, evidence, review, or integration governance.


Every control event derives one scheduling projection from the entire canonical TASK_LEDGER, not only the triggering task, package, or business line. READY and dependency-cleared PENDING work share the same ephemeral runnable projection; a PENDING parent with multiple explicitly separable action clauses may expose only the dependency-cleared clause as an ephemeral derived slice while the authoritative parent row remains PENDING. Existing ACTIVE or VERIFY work in Web, Mini, or Server may consume capacity or impose a real conflict, but it must not hide unrelated runnable work elsewhere in the project. When multiple runnable packages are mutually non-conflicting and machine-derived capacity is available, the receipt must account for them project-wide and fill available dispatch capacity; soft deferral while capacity is idle fails closed, and active dispatch decisions may not exceed available capacity. A registered Controller Stop/Yield receipt additionally carries the fixed ordered control loop: read project facts → consume pending terminal/reviewer/candidate/recovery events → derive project-wide runnable → derive pending slices → compute capacity/conflicts → decide every runnable → dispatch available capacity → execute every immediate Controller-owned action → recompute after actions. Candidate/review/integration/acceptance/recovery/ACK work remains Controller-owned even while Writers are ACTIVE. Any deterministic failed control cycle becomes a mandatory correction derived from the same immutable controller-cycle evidence; correction shares this canonical projection, requires execution plus independent verification, and remains Stop/Yield-blocking until closed. Stable recurrence fingerprints are derived evidence only; repeated root causes escalate L1→L4 policy severity but never create another scheduler, task ledger, READY namespace, or logical Controller.
