# Controller Performance Scoring

> 用于评估长期项目唯一总控 / orchestrator 的近期履职质量。评分对象是“总控如何推进项目”，不是某个 Writer、Reviewer 或单次模型调用本身。
>
> 核心原则：**不奖励忙碌，奖励基于真实证据推动关键路径发生有效状态变化。** 前端页面、后端代码、数据库约束、基础设施、治理规则、测试、独立审查等，只要与当前 Goal 直接相关且可验证，都可以构成真实成果；“用户肉眼可见”不是成果的必要条件。

## 1. 评分口径

### 1.1 默认评估窗口

除非用户明确指定，采用：

- 以**最近 24 小时**作为主时间边界，在该边界内按时间倒序选取**最近 5 个有效控制事件**作为正式事件样本；少于 5 个时取实际全部，不人为补齐；超过 5 个时取时间上最近的 5 个，**不得在 24 小时内挑选更漂亮的 5 个**；
- “有效控制事件”必须能够用机器事实评价总控行为，例如形成明确 dispatch / recovery / review / integration / Goal rollover / blocker 处理决策及其可验证结果；重复 Hook 提醒、重复读状态、同一决策的多次通知不得拆成多个事件刷样本；
- 另外单独检查**当前所有重大未闭环异常、关键路径停滞和未闭合控制事件**。它们用于修正相应维度、触发 Anti-Gaming / 封顶或解释当前风险，**不得作为额外控制事件重复计分**；
- 若最近 24 小时内事件过少，应明确写“样本不足”并报告实际事件数；**不得为了凑满 5 个事件**把更早的漂亮成果拉入主评分窗口。更早证据只能作为历史对比基线；
- 正在执行、尚未形成可验证状态变化的工作，只做趋势观察，不提前计成功分；
- 历史里程碑可作为对比基线，但不得直接给当前窗口加分。

**Controller Self-Check 与正式评分分层：** Self-Check 必须继续从当前精确安装的正式评分模型派生，但只用于纠偏当前行为；**不得执行完整的 24 小时 / 5 事件正式评分**，不得自行计算七维分，也**不得暴露实时总分**。正式评分负责长期稳定衡量与趋势历史，Self-Check 负责轻量即时纠偏，两者不得合并成一套重型循环。

每次评分必须明确写出：

1. 评估窗口；
2. 事实截止时间；
3. 当前 main / 当前 Goal；
4. 采用的关键证据；
5. 是否触发总分封顶规则。

### 1.2 历史回溯先锁定总控任期

当用户要求评估“刚进入开发阶段”“这任总控刚接手时”“某次换控后的表现”等历史阶段时，必须先定位该总控的**任期起点**：以明确的接管 / 换控消息、controller session / thread、交接记录或机器注册证据为准。不得从第一笔漂亮交付、第一次 `feat`、某个高分里程碑或方便取证的提交开始截窗口。

历史评分必须遵守：

- 先确定本任总控接管时间与结束 / 继任边界；
- 不得把前任总控的成果、失误、人工唤醒或控制债务混入本任，也不得把继任者的修复反向给本任加分；
- 若任期内发生多次 context handoff，但职责主体没有更换，应视为同一总控任期的续接，不因换 session 自动清零历史问题；
- 若证据不足以证明接管 / 换控边界，应明确写“任期边界不确定”，不得为了得到更好分数自行选择窗口。
- 需要比较“上次 / 最近一次评分”时，必须先定位同一总控下**最近一次有效评分**的可验证记录，并确认其总分、评分窗口与证据来源；正式评分通过机器门后，应在 Git common-dir 的 Adaptive Agent Runtime 评分历史索引中留下最小摘要（controller/session、时间、总分、窗口摘要、模型哈希、turn/message 证据引用）。查询优先使用该索引；无法确认任一项时，该历史基线记为 `UNKNOWN`，不得根据模型记忆、语义印象或其他历史分数推断“上升 / 下降”。

### 1.3 事实优先级

评分优先使用可独立核验的事实：

1. 当前唯一 `main` / worktree / diff / commit / candidate；
2. 真实测试、Harness、真实端或外部服务验收证据；
3. Assignment、delivered ACK、Reviewer verdict、控制收据、生命周期状态；
4. `TASK_LEDGER.md` 当前状态与依赖；
5. 总控活会话中的调度行为与解释。

单纯自然语言自述不能覆盖 Git、测试、运行状态或台账事实。

### 1.4 责任归因：先判断“谁可控制”，再扣分

对评分窗口内每个重大停滞、返工、人工唤醒、失败恢复或控制面异常，必须先做**责任归因**，至少使用以下四类之一：

- `controller-caused`：总控在其可控制范围内选择错误、漏派、漏恢复、错误验收、错误优先级或未持续推进；
- `governance-caused`：Adaptive Agent Runtime、Hook、handshake、lifecycle、机器门、规则安装/迁移等治理基础设施本身造成；
- `external-caused`：供应商、授权、配额、外部服务、不可控环境或用户明确暂停造成；
- `mixed`：总控行为与治理 / 外部因素共同造成，必须拆出各自可归责部分。

归因规则：

- **不得把治理基础设施导致的停滞直接记为总控失职**；同理，真实 external-caused 时间不能按 controller-caused 全额扣分。
- `governance-caused` / `external-caused` 只豁免总控不可控制的那一段；如果总控在阻塞解除、规则生效或替代路径可用后仍未及时 reconcile / dispatch / recovery，后续新增停滞可转为 `controller-caused` 或 `mixed`。
- 归因必须绑定证据和时间边界，不能因为“系统最近改过规则”就把整个窗口一律免责。
- **困难环境本身不加分**，也不得设置困难系数、逆风 bonus 或人工补偿分。环境复杂度只影响责任归因，不直接改变七维权重。
- **适应能力**只在出现可验证行为时进入现有维度：总控能主动 reconcile 新规则 / 新事实源，识别旧 blocker 已失效，选择合法替代路径，并且**不需要用户实质接管**就恢复关键路径。该证据可提高“异常恢复与任务流转”“调度与执行效率”“控制面一致性与可审计性”，但同一事实不得重复放大成果价值。

## 2. 七维评分模型

| 维度 | 权重 | 核心判断 |
| --- | ---: | --- |
| 有效成果与 Goal 推进 | 25% | 项目是否基于真实证据从状态 A 推进到状态 B，尤其是否推动当前 Goal / 关键路径 |
| 任务拆解与边界设计 | 15% | Goal 是否被拆成粒度合理、单目标、依赖清晰、可分派、可验收的工作包 |
| 关键路径与优先级 | 15% | 是否优先解决真正阻塞里程碑 / 用户主路径 / 高风险的问题，而不是挑容易小任务 |
| 调度与执行效率 | 15% | Agent 路由、并行、WIP、checkpoint、空转识别、成本与返工是否合理 |
| 质量、验收与证据 | 10% | 是否有与风险相称的真实测试、独立审查、真实端 / 环境验证和完整证据链 |
| 异常恢复与任务流转 | 10% | 失败后是否快速形成新证据、有效恢复并重新进入 candidate / review / integration 流 |
| 控制面一致性与可审计性 | 10% | Goal、台账、Assignment、ACK、Git、候选、Hook / receipt 是否一致且可追溯 |
| **总计** | **100%** | |

### 2.1 原始分与加权分口径（固定）

七个维度的**原始分统一采用 0–100 分制**，不得改用 10 分制、维度权重满分制（例如 20/25）或其他临时归一化口径。**加权分 = 原始分 × 权重**，例如“有效成果与 Goal 推进”原始分为 `96`、权重为 `25%` 时，`96 × 25% = 24.00`。七项加权分相加得到 100 分制总分，再应用第 6 节封顶规则。

正式明细表固定使用以下列：

`评分维度 | 权重 | 原始分 | 加权分 | 主要判断`

这只是评分呈现与计算契约；第 3 节某些维度内部的 10+9+6 等拆分仅用于帮助判断该维度的 0–100 原始分，不得直接拿内部子分替代原始分列。

### 2.2 单回合诊断：能力上限 / 下限，不生成第二套正式评分

需要判断总控“一个完整闭环最好能做到什么、最差会掉到什么程度”时，可以执行**单回合诊断**。它复用完全相同的七维、0–100 原始分、权重、责任归因与封顶规则，只把观察单位从 24 小时窗口改成一个完整控制回合：从明确控制决策 / dispatch 开始，经监控、recovery（如有）、review、integration / blocker 决策，直到形成可验证终态。

- 单回合诊断只记录能力样本，**不得反向改变 24 小时正式总分**，也不得覆盖正式评分历史；
- 只有 `CLOSED / FAILED / BLOCKED / CANCELLED / ABSORBED / PARKED` 等有可验证终态的回合可进入历史；**尚未终结**、仍 `READY / ACTIVE / VERIFY / RECOVERING` 的回合只观察，不得进入最佳 / 最差排名；
- **最佳闭环回合**与**最差闭环回合**只能在同一 Controller、**同一评分模型**哈希下比较，模型变化后旧样本不得直接参与新模型极值；
- 每个单回合记录至少保存 `cycle_id`、终态、总分、模型哈希、事实 / 证据摘要与消息证据引用；最佳 / 最差是从这些合格记录中按总分选出的诊断极值；
- 诊断目标是看“上限是否够高、下限是否持续抬升”，不是鼓励挑漂亮回合刷正式成绩。

单回合输出必须包含：`单回合诊断评分：N/100`、`控制回合：<cycle_id>`、`回合终态：<terminal>`、`证据摘要：<evidence>`。只有再提供 `证据收据：<event_id>`，且该 ID 能读取到 `control_event_guard.py` 为同一逻辑 Controller、同一控制事件预先生成的不可变**机器证据收据**时，记录才能以 `record_kind=cycle` 进入最高 / 最低分；仅凭回复自报的终态和证据只能保存为 `record_kind=cycle_candidate`，不得进入极值。

正式评分还必须同时报告同一 Controller、同一评分模型下的历史诊断极值：`单回合最高分`、`最高回合`、`单回合最低分`、`最低回合`。机器历史中没有合格终态样本时，这四项必须明确写 `UNKNOWN`，不得根据聊天记忆、当前正式分或未持久化回合补造极值。

## 3. 各维度评分标准

### 3.1 有效成果与 Goal 推进（25%）

不按任务数量或 commit 数量累计，而看**关键状态变化的价值和闭环程度**。

成果可来自不同任务类型：

- 前端 / UI：真实页面行为、交互、端侧验收；
- 后端：API、数据库约束、业务逻辑、迁移、真实测试、候选与集成；
- 基础设施：Hook、运行时、部署、自动化流程及其真实生效证据；
- 治理：机器门、receipt、自动检查、安装生效；
- Reviewer：独立 verdict + 对精确 revision 的证据；
- 调研：可追溯证据支撑、且直接改变产品 / 技术决策的结论。

推荐内部拆分：

- 成果真实性：10 分；
- 对当前 Goal / 关键路径的推进价值：9 分；
- 当前任务链闭环程度：6 分。

**动作不算成果，状态变化才算成果。** `RUNNING`、PID 存活、调用次数、token、读文件、跑命令、写计划、台账提交本身均不自动产生本项得分。

### 3.2 任务拆解与边界设计（15%）

重点看：

- 一个 Assignment 是否只有一个明确 Primary Goal；
- 是否把 Goal 拆成 Agent 能独立负责、结束后可 PASS / FAIL 的工作包；
- 粒度是否适中：既不是“把整个后端改好”，也不是“打开文件 / 搜索 / 改一行”这种操作步骤；
- 依赖是否拆对：能并行的互相独立，有依赖的必须串行；
- ownership / owned files / 禁止范围是否清楚；
- success criteria 是否事前明确并可验收；
- 拆解是否减少冲突、返工和审查成本，而不是制造更多任务卡片。

### 3.3 关键路径与优先级（15%）

重点看：

- 当前 Goal 是否服务项目级关键路径；
- 是否优先处理阻塞更多后续任务、用户主路径或高风险问题的工作；
- 是否因为容易完成而长期绕开困难阻塞；
- 是否在关键路径受外部硬阻塞时，合理利用剩余容量推进真正独立的 READY；
- Goal 选择不能只基于当前局部任务，而必须结合项目级依赖重算。

### 3.4 调度与执行效率（15%）

重点看：

- 模型 / Agent 是否按任务能力正确路由；
- 并行是否基于依赖关系，而不是 Agent 数量；
- WIP 是否合理，唯一集成流是否保持受控；
- checkpoint 是否足够早发现偏航、空转、重复探索；
- 同等成果下，是否存在明显异常的 model calls、时间、重试和返工；
- 是否不必要地亲自下场开发，挤占总控的调度、审查和恢复注意力。

Agent 数量、并发数量、消息数量本身均不加分。

**人工唤醒 / 自主续作是调度质量的直接证据。** 在没有真实外部阻塞、授权门或明确暂停条件时，如果 READY / ACTIVE / VERIFY 工作反复停在说明、同步、等待或空转状态，必须由用户发送“继续”“怎么停了”“在干活吗”等指令才恢复，则记为人工唤醒。一次偶发中断不自动判失职，但同一结果链反复需要人工唤醒，说明总控没有持续把任务推进到下一可验证状态。评分时必须同时检查：

- 是否有真实外部阻塞，而不是把内部可执行动作伪装成等待用户；
- 用户唤醒后是否只是恢复原本就应自主完成的 dispatch / recovery / review / integration；
- 总控是否让用户实质接管派发 / 恢复 / 验收，替总控决定“谁继续、何时恢复、哪些任务可并行”；
- 是否出现“用户不发下一句话，关键路径就长期不再推进”的模式。

人工唤醒主要扣减本项，同时影响异常恢复与控制面一致性；不能因为最终仍产出代码而把这种失控成本抵消。若事件被可靠归因为 `governance-caused` / `external-caused`，不得把对应不可控等待伪装成总控调度失职；但阻塞解除后总控是否自主恢复，仍属于本项。

在规则或运行环境发生实质变化时，若总控主动 reconcile 新规则、重算可执行工作、切换到合法路由并恢复 dispatch，可作为调度适应能力的正向证据；仅“读到了新规则”或等待用户告知下一步不加分。

### 3.5 质量、验收与证据（10%）

重点看：

- 测试是否真正针对当前风险，而不是容易 PASS 的弱测试；
- evidence 是否绑定精确 revision / 环境；
- Writer 自检与非作者 Review 是否区分；
- 高风险变更是否有相称的 Harness、真实端或外部服务证据；
- 是否完整报告 PASS / FAIL，而不是只挑成功片段；
- 决策能否反向追溯到证据。

**视觉基线失守属于质量门失效，不是普通 UI bug。** 对有绑定参考图、目标端规范或明确视觉事实源的任务，开工前必须核对精确绑定参考、适用页面 / 状态 / 视口与目标端规范。若因为使用错误参考图、错误尺寸 / 视口、混用另一端规范或跳过已绑定视觉事实源，导致明显偏离、整批返工或已给出的视觉 PASS / DONE 被撤回，必须在本项显著扣分。若用户先于内部验收指出肉眼明显偏差，说明现有质量门未发挥作用；不得把后续修正重新包装成额外成果。

当视觉基线失守造成“已验收 → 撤回 → 重新实现”时，至少要记录：原验收依据、错误基线、撤回证据、受影响范围、重新验收证据。若这些信息缺失，则同时降低控制面一致性。

### 3.6 异常恢复与任务流转（10%）

重点看：

- 失败 / 卡死后是否快速识别真实原因；
- recovery 是否绑定同一 Assignment / 可验证恢复动作，而不是机械重开 Agent；
- 恢复后是否产生比失败前更多的有效知识或项目状态变化；
- 是否及时从 RED → 修复 → GREEN → candidate → review → integration；
- 连续恢复如果没有新增 evidence / diff / HEAD，应视为空转而不是“持续管理”。

**恢复动作不重复累计成果。** 只有项目状态超过之前最佳检查点，才重新产生新的成果价值。

若失败主要来自 `governance-caused` / `external-caused`，不要因不可控失败本身扣总控；重点评价总控在条件变化后能否主动识别新可用路径并恢复到 candidate / review / integration。无需用户实质接管即可完成这类恢复，是适应能力的强正向证据。

### 3.7 控制面一致性与可审计性（10%）

重点看：

- Goal、TASK_LEDGER、Assignment、delivered ACK、Git、candidate、Hook / receipt 是否一致；
- ACTIVE / RECOVERING 是否有真实执行绑定或可验证恢复动作；
- candidate 是否来自精确 HEAD，是否被正确 Review / absorbed / parked；
- 规则版本 / loaded ACK 是否及时同步；
- 行为层展示与本地事实发生漂移时，是否及时 reconcile；
- 控制面 commit 不得冒充产品交付进展；
- 治理规则或机器事实变化后，是否主动 reconcile loaded revision、ledger、Assignment、blocker 与实际可执行路径；能够在不需要用户实质接管的情况下完成一致性恢复，可作为适应能力证据。

## 4. 成果等级：防止“小任务刷分”

同一个结果链不按步骤重复累计；成果按对 Goal 的影响分层：

- **L1 局部动作**：单个测试、文档、局部整理、无依赖解锁的小改动；
- **L2 有效子任务**：明确 bug 修复、永久 RED、独立 Review PASS、可验证子目标完成；
- **L3 关键路径成果**：移除 blocker、形成关键 candidate、解锁后续依赖；
- **L4 Goal / 里程碑闭环**：candidate → review → main → regression / acceptance → Goal CLOSED / rollover。

`10 × L1` 不自动等价于 `1 × L4`。评分看关键路径和状态推进，而不是数量求和。

## 5. Anti-Gaming Rules（防刷分规则）

### 5.1 禁止挑评分窗口

不得只挑刚完成的漂亮任务。默认主窗口必须使用最近 24 小时内时间上最近的最多 5 个有效控制事件，并单独检查当前所有重大未闭环异常 / 关键路径停滞；不得用最后两件漂亮事件覆盖整日表现。

### 5.2 禁止事后缩小 Goal

Goal 和 success criteria 应在执行前登记。中途缩 Goal 必须记录：原 Goal、变更原因、触发证据、剩余工作去向；剩余工作不得消失。

### 5.3 禁止挑简单 READY 绕开关键阻塞

大量完成低价值小任务不能补偿项目级关键路径长期停滞。

### 5.4 Blocked / Parked 必须有机器可验证依据

困难任务不能因为难做就标 `blocked / parked`。必须有具体阻塞源、wake condition / retention reason；仍有内部恢复动作时不得冒充外部阻塞。

### 5.5 禁止拆碎任务刷完成数

同一结果链中的“读文件 → 写测试 → 修代码 → 跑测试”是一个任务生命周期，不分别累计成多个成果。

### 5.6 禁止重复修复刷分

修坏、恢复、再修同一问题不重复计成果；只有超过此前最佳验证状态才产生新的推进价值。

### 5.7 控制面繁荣与 Delivery 分开

ledger / governance commit 说明管理动作，但除非当前 Goal 本身就是治理升级，否则不能代替代码、候选、验收、blocker removal 等实际 Delivery。

### 5.8 禁止弱测试和选择性证据

测试必须证明具体风险；验收必须记录完整命令 / 环境 / revision / 结果摘要，不能只展示成功片段。

### 5.9 禁止作者伪装非作者 Reviewer

换 prompt、换 session 不等于独立 Reviewer。Reviewer 必须独立 Assignment、非作者身份，并审精确 candidate revision。

### 5.10 不奖励无效并发与高成本堆结果

同等成果下，大量不必要 Agent、model calls、长时间空转和重复返工应降低调度效率分。

### 5.11 一个事实不可重复放大价值

同一 evidence 可支持多个维度判断，但不能在多个维度重复按“成果价值”大幅加分。例如 `RED 2/2` 可证明成果真实性和质量，但不能同时被算成四份独立成果。

### 5.12 区分有效失败与无效空转

失败后如果获得可验证的新知识并改变下一步，是有效探索；如果只是重复读取 / 尝试、没有新增 evidence / diff / decision，则只算成本。

### 5.13 人工介入不能被最终交付抵消

如果没有真实外部阻塞，却需要用户反复人工唤醒、重新派发、提醒继续执行或指出应并行的独立 READY，后续最终交付只能证明“任务后来完成”，不能抹掉此前自主续作失败。评分必须报告人工唤醒次数与其触发的实际恢复动作。

### 5.14 视觉返工不能刷成果

因未核对绑定参考图 / 目标端规范造成的视觉返工，只能恢复到此前应有的质量基线；修正错误参考、重新截图、重新验收本身不重复计为新的高价值成果。视觉 PASS / DONE 被撤回时必须按视觉基线失守处理。

### 5.15 不用“困难环境”直接加分

困难环境本身不加分。不得设置困难系数、逆风 bonus 或因为 governance 频繁变化而人工抬高总分。正确做法是先做责任归因：不可控部分不误扣，可控部分照常评价；只有总控展示了可验证的自主适应 / 恢复行为，才在既有七维中获得相应正向评价。

## 6. 总分封顶规则

先算七维加权分，再应用以下上限；多个上限同时出现时取最低值：

- **关键路径连续明显停滞，且总控持续把资源投向低价值旁支**：总分最高 `79`；
- **同一评分窗口内，在无真实外部阻塞情况下出现至少 2 次人工唤醒，且唤醒内容只是恢复总控本应自主完成的 dispatch / recovery / review / integration**：总分最高 `69`；
- **用户实质接管派发 / 恢复 / 验收，反复替总控决定谁继续、何时恢复或哪些 READY 应并行，说明自主调度持续失控**：总分最高 `59`；
- **视觉基线失守导致已宣称的视觉 PASS / DONE 撤回，或错误绑定参考造成整批明显返工**：总分最高 `69`；
- **存在把无证据状态宣称为完成 / 候选 / PASS 的虚假成果**：总分最高 `69`；
- **Goal、台账、Assignment、Git / candidate 存在严重事实冲突且未及时纠正**：总分最高 `59`；
- **发生作者自审冒充独立审查、失败候选绕过门禁进入 main 等重大治理违规**：事故未纠正、事实未对齐或同类风险仍在重复时，治理风险状态为 `RED`，风险约束分最高 `49`；事故本身已纠正但解除证据尚未闭合时，治理风险状态为 `AMBER`，该上限继续保留。

重大治理事故的 `49` 分上限是一笔需要证据偿还的治理风险债，不是按自然时间衰减的永久惩罚。**时间经过本身不能解除**。只有以下条件全部有当前证据时，才可把这笔事故对应的治理风险状态恢复为 `GREEN` 并解除该项上限：

1. 事故候选已在当前 main 完成纠正，经过相称的非作者审查、回归 / 真实环境验收，并与台账、远端状态（如适用）闭合；
2. Controller 身份、唯一所有权、运行时 / 机器轨迹、loaded revision、当前 main `HEAD` 与唯一台账完成**控制面对齐**；
3. 事故纠正之后至少新增一个无门禁穿透、证据完整的**后续高价值闭环**，达到 L3 或 L4，并形成同一 Controller、同一评分模型下的合格终态回合记录；
4. 本次解除判断在正式评分证据中逐项列出，缺任一项即保持 `AMBER` 与原上限；若同类事故再次发生则回到 `RED`。

机器解除链不得只相信上述自然语言。`corrects_incident` 必须绑定已进入 current main 的精确纠正 revision；纠正作者、纠正任务和非作者 `PASS` Reviewer 必须相互一致，且对应任务必须真实存在于当前台账并已成功终结；同时还要有回归与真实环境验收。若 main 配置了跟踪远端，则远端引用必须可解析且 revision 与 main 一致，缺失引用也按未闭合处理。`post_incident_closure_for` 必须绑定该事故的精确纠正证据 ID；同一事故存在多次纠正时，任一条“纠正 → 对齐 → 后续 L3 / L4”的完整精确链均可解除，不能因更早的不完整尝试阻断，也不能用无关 L3 / L4 回合替代。普通草稿被门禁拦下只形成失败回合证据，不自动制造 `49` 分债；只有历史已确认重大事故，或机器确认已集成后仍发生 Review / 回归门穿透，才自动进入重大风险投影。

强纠正收据带机器能力版本。旧版弱纠正收据只能把事故推进到 `AMBER`，不得直接参与解除；后续闭环必须绑定强纠正收据。同一事故有多次强纠正时，任一条完整精确证据链均可解除，不被更早的不完整尝试阻断。

解除只影响当前风险约束，不回写过去的正式评分，也不删除事故回合；**历史最差闭环回合仍保留**，直到同一模型下出现更低的合格终态样本或模型版本变化后重新建立样本集。

`80+` 应要求关键路径有真实推进且主要证据链完整；`90+` 通常要求近期窗口至少形成一个高价值 L3，并接近或完成 L4 闭环，同时没有明显控制面债务或持续空转。

### 6.1 三层评分呈现

正式评分不得只给一个被封顶后的数字，必须分开报告：

- **近期履职能力**：七维原始分按固定权重相加后的加权总分，尚未应用第 6 节上限；它回答“近期实际调度与交付能力表现如何”。
- **治理风险状态**：`GREEN / AMBER / RED`，并附当前事实依据；状态必须匹配评分请求开始时绑定到逻辑 Controller 的**机器风险投影**，不得由评分回复自由选择。机器投影发现失败控制事件或历史 `49` 分重大事故时进入 `RED`；有纠正收据但控制面对齐或后续 L3 / L4 收据未闭合时为 `AMBER`；全部机器条件闭合后才为 `GREEN`。
- **风险约束分**：对近期履职能力应用所有当前有效上限后的分数；保留兼容字段 `score` 时，其值必须等于风险约束分，且风险约束分不得高于近期履职能力。

风险约束分是当前可授予的治理信任分，不得反向冒充能力原始表现；近期履职能力也不能绕开风险约束被表述为正式总分。

## 7. 分数解释

- `90–100`：强履职。关键路径持续推进，拆解、调度、证据、恢复和闭环均稳定；
- `80–89`：良好 / 强胜任。真实推进明显，存在少量效率或控制面问题；
- `70–79`：胜任但不稳定。治理基本正确，但吞吐、恢复、关键路径选择或闭环存在明显短板；
- `60–69`：勉强。存在持续停滞、弱证据、错配调度或较大一致性问题；
- `<60`：明显失职或控制面失真，需要优先纠偏。

## 8. 标准评分输出模板

每次评分至少给出：

1. **三层评分**：`近期履职能力：N/100`、`治理风险状态：GREEN / AMBER / RED`、`治理风险依据：...`、`风险约束分：N/100`；
2. **评估窗口与事实截止时间**；
3. **七维明细表：评分维度 / 权重 / 原始分 / 加权分 / 主要判断**；
4. **本窗口最高价值成果（L1–L4）**；
5. **最大扣分点**；
6. **是否触发防刷分 / 封顶规则**；
7. **责任归因结论**：重大停滞 / 返工 / 唤醒分别属于 `controller-caused`、`governance-caused`、`external-caused` 或 `mixed`，以及哪些扣分被豁免、哪些仍归总控；
8. **人工介入 / 自主续作结论**：是否存在无外部阻塞下的人工唤醒，用户是否实质接管调度；
9. **视觉基线核对结论**：有视觉任务时是否绑定了正确参考图与目标端规范，是否发生视觉基线失守 / 撤回；
10. **同模型单回合极值**：`单回合最高分：N/100`、`最高回合：<cycle_id>`、`单回合最低分：N/100`、`最低回合：<cycle_id>`；无合格记录时四项均写 `UNKNOWN`；
11. **下一次升分或解除风险上限必须出现的真实状态变化**。

评分不是为了让数字好看，而是为了判断：**总控有没有选对事情、拆对任务、派对执行者，并基于真实证据把项目关键路径持续推向完成。**
