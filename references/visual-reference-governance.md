# Visual Reference Governance

视觉参考是项目级事实，主 Agent、设计、开发、测试和验收角色共同遵守。

## 状态

- **探索稿**：仅讨论，不归档为有效参考。
- **认可参考图**：用户明确说“作为参考”“按这个开发”“保留给后续角色”等；可带已知瑕疵。
- **运行时资产**：需要单独确认；参考图不会自动成为上线素材。
- **已替代**：从有效基线移出或明确标记，后续不得静默复用。

“不错”“有感觉”等模糊评价不自动升级；若用户已明确认可，不再重复询问是否归档。

## 探索到定稿的阶段门

视觉设计按“候选方向 → 探索稿 → 明确认可精确图片 → 记录与治理”推进。用户同意候选方向、页面清单、制作方式、继续探索或图片调用，只授权下一步，不等于认可任何具体图片或确认视觉事实。

精确图片未获明确认可前，不以视觉治理为由修改 `DESIGN.md`、视觉参考索引或当前任务台账；候选方向、比较结论和待决问题只保留在当前任务计划或项目约定的临时探索目录。若项目明确要求台账记录所有进行中工作，台账只记录“视觉探索中”和交付物位置，不把候选内容写入已确认决定。

用户独立确认的产品行为可以按项目文档职责同步到 `SPEC.md`，但不得因此把未认可的图片或视觉方向升级为有效参考。

## 明确认可后的动作

只执行记录和治理，不擅自开始 UI 实现：

1. 锁定被认可的精确图片；无法取得或无法区分版本时才请用户重新提供。
2. 新项目在首张认可图出现时创建 `design-references/`；现有项目沿用 `development-reference/` 等既有约定，不强制迁移。
3. 保存原图并在 `DESIGN.md` 登记路径、适用范围、采用点、不得照搬的瑕疵和状态。
4. 把采用点转写成可执行视觉规范，而不只保留图片说明。
5. 在当前唯一任务台账同步当前视觉决定及真正受影响的下一步。

小瑕疵不构成重新生成图片的理由；未经请求和费用授权，不调用图片模型。只有产品行为或技术资产契约确实变化时，才影响扫描 `SPEC.md` 或 `TECHNICAL.md`。

### 已确认参考图快速路径

用户已明确认可、精确图片可定位，且没有新的产品行为、运行时资产契约或外部操作时，强制使用快速档；不能仅因需要同步多份权威文档升级为标准档。

1. 锁定图片并检查文件、尺寸和摘要。已知路径时不重读旧会话；确需从任务定位时，只做一次最近相关文本轮次的有界读取，不包含工具或图片输出，仍无法定位时直接请求精确文件，不继续翻页。
2. 按项目文档职责做定向影响扫描：参考索引必须更新；可复用视觉或组件规则变化时更新对应 `DESIGN`；当前目标、阻塞或下一步变化时更新状态账本；只有产品行为变化才更新 `SPEC`，只有运行时资产或技术契约变化才更新 `TECHNICAL`，只有形成可复用方法才更新经验文档。
3. 归档图片并更新所有真实受影响的事实源，不机械修改无关文档。
4. 搜索旧路径、旧状态和冲突规则残留，检查本地链接、摘要和文档差异后立即停止。

快速档减少无关流程，不减少必要影响扫描。图片版本不明确、认可参考互相冲突、扫描发现跨域变化或操作触及费用、外部写入、删除等边界时，停止快速路径并按实际风险升级。不得重新讨论已确认设计、重看无关候选、重新调用图片模型、广泛读取记忆或加载与归档无关的规划和验证流程。

## 使用与验收

视觉任务开始前读取 `DESIGN.md` 及其中登记为有效的精确文件。不得依据 `final`、`v2`、更新时间或“看起来最完整”推断批准。

设计角色延续采用点并避开排除项；开发角色按同一基线实现；测试与验收角色同时检查“应采用”和“不得照搬”；主 Agent 处理替代、冲突和状态同步。聊天记录和每个 Agent 的私有清单都不是视觉事实源。

### 绑定视觉基线

用户明确要求严格遵循视觉规范、与参考图风格一致，或项目把精确图片标为完整视觉定稿时，该图片是绑定视觉基线，不是可自由改写的灵感。它约束适用范围内的结构、比例、层级、留白、字体、色彩、间距、表面、边框、圆角、阴影、密度、组件语言和状态；示例内容、错字、伪图标、截图像素与已登记排除项不得照搬。任何设计或前端专项方法都从属于该基线；不得另起一套视觉系统，也不能借“提升设计”“响应式适配”或“参考图不是运行时资产”为理由偏离该基线。

参考图未覆盖的新区域或组件，从语义最接近的已确认组件派生最小变体，并保持同一 Token、几何语言、密度与交互状态；现有组件能承载时直接复用。无法可靠找到派生源、参考之间冲突或缺少必要获批运行时资产时，登记视觉决策或资产阻塞，不得用临时插画、粗糙 CSS、候选资产或通用组件冒充完成。

项目台账只登记本项的精确参考路径与摘要、确认层级、适用范围、采用点、排除项、新组件派生关系、规定视口与状态、证据位置和当前结论；通用方法只保留在本参考。

### 完成硬门

首个可运行界面出现后立即做一次定向视觉比较；冻结候选后再做完成验收。使用同状态、规定视口的真实端截图，记录 CSS viewport、浏览器缩放、设备像素比和实际截图像素，并逐项判断结构、比例、层级、风格与响应式结果。截图存在不等于视觉通过，文件名也不能替代实际元数据；参考内容不同不妨碍对照视觉合同。

视觉偏差、错误缩放、未映射的新组件或资产阻塞未消除时保持 `VERIFY`，不得提交、标记 `DONE` 或声称视觉完成。独立审查主体可用时，绑定视觉里程碑由非作者复核同一候选与截图；主 Agent 仍负责最终对照。

需要机械守卫时使用：

```bash
python3 scripts/visual_evidence_guard.py path/to/visual-receipt.json
```

收据包含 `references(id, path, sha256, role=binding, states)`、`approved_components(id, reference)`、`required_runtime_assets`、`runtime_assets(id, path, sha256, approval=approved)`、`required_viewports`、`required_states`、`captures(state, reference, viewport, screenshot, browser_zoom, device_scale_factor, capture_source, source_revision, checks, verdict)` 和 `uncovered_components(name, derived_from)`。守卫验证参考摘要与适用状态、同状态矩阵、PNG 实际像素、缩放、真实运行入口声明、五类比较结论、获批素材和已登记组件派生关系。

机械守卫不能证明自报的浏览器、DPR、运行提交或检查结论真实，也不能仅凭组件 ID 判断它是否真是语义最接近的派生源；完整可解码的 PNG 和正确尺寸仍不等于视觉内容合格。非作者复核必须打开实际候选、精确参考和证据，核对运行来源、同状态、派生合理性与素材授权后才能通过。
