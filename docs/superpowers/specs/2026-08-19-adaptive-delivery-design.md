# Adaptive Delivery 设计规范

## 1. 目标与边界

`adaptive-delivery` 是一个可安装的 AI 编程代理 Skill，用于在项目初始化、多阶段交付、跨会话协作、视觉基线治理、验证与发布、以及经验提炼时选择合适的工程方法。它连接需求、设计、开发、测试、验收和发布的事实，但不取代项目自己的测试工具、CI/CD 或发布平台。

Skill 的默认目标是最小可验证闭环，而不是为每个软件问题加载完整编排。任何 Git 写入、付费调用、外部发布或全局规则修改都必须停在相应授权门前。

## 2. 三档自动裁剪

Skill 根据范围、风险、依赖和用户目标自动选择档位；信息不足时先读取当前事实，必要时升级档位。

| 档位 | 适用条件 | 默认动作与证据 |
| --- | --- | --- |
| 快速档 | 目标明确、低风险、小范围，通常不跨边界 | 直接执行；读取相关事实，做能证明改动的最小检查，达到停止条件立即结束。 |
| 标准档 | 普通功能、UI 调整或跨文件改动 | 先给简短计划，说明依赖、所有权和验证；只做必要协调与定向证据。 |
| 严格档 | 认证、费用、外部调用、持久化迁移、安全边界、正式安装、部署或发布 | 完整门禁；覆盖适用的成功、未配置、认证失败、超时、取消、恢复、迁移、回滚和独立审查证据，并在授权前停止。 |

低风险工作不得因“属于软件开发”而自动升级；发现新风险时可以从快速档升级到标准档或严格档。

进入开发阶段时，标准档或严格档必须先按项目实际情况给出里程碑与验收、工作包与依赖、负责人或 Agent、文件所有权、交付物、验证和停止条件。只制定计划不授权代码修改；开始开发才按已确认计划执行；继续开发从 `PROJECT_STATUS.md` 和当前工作区续接，不重做已完成内容。

用户不必逐字输入固定口令。自然语言意图明确时可直接识别“只规划”“按确认计划执行”或“从当前状态续接”；写入授权含糊时只做事实对账并请求确认。当前状态来自状态账本、Git 和权威文档，不能由旧聊天或过时记录覆盖。

## 3. Skill 触发范围

自动加载完整 `adaptive-delivery` 编排的范围仅包括：

1. 项目初始化或协作文档缺失。
2. 需求到设计、开发、测试、验收、发布的多阶段交付。
3. 跨会话续接、状态对账或共享工作区协作。
4. 视觉基线、参考图归档或视觉验收治理。
5. Harness、发布画像、安装、迁移、部署或回滚门禁。
6. 从有证据的项目事实提炼可复用经验。

普通问答、单文件简单修改和普通代码审查，不得仅因属于软件开发就加载完整编排。用户明确要求使用 Skill 时仍可显式进入，并按三档裁剪。

### 3.1 平台普适性与适配边界

- `SKILL.md`、references、模板和脚本使用平台无关的项目、会话、主协调 Agent 与执行 Agent 概念，不把 Codex、Claude Code、Gemini CLI、Cursor 等任一产品作为运行前提。
- 自动发现、显式调用语法、安装目录和全局指令文件属于宿主能力。README 只把经过核实的平台方式列为接入示例，不承诺所有 Agent 都能自动加载 Skill。
- 兼容 Agent Skills 的宿主可直接安装；不兼容的 Agent 仍可通过自然语言要求其读取 `SKILL.md` 和项目事实源来采用同一方法。
- `AGENTS.md` 是默认的项目启动与路由入口。若宿主使用其他指令文件，只在该入口链接现有权威文档，不复制需求、视觉、技术或状态细节。
- `$adaptive-delivery` 只是部分宿主支持的显式调用示例，不是使用方法论的必要条件。
- 平台差异只出现在 README 的短接入说明中，不为每个平台复制一套 Skill、references、模板或测试。

## 4. 所有任务的共享硬约束

无论档位，始终只保留以下硬约束：

- 先读取当前事实源、工作区状态和已有实现。
- 保护用户及其他任务已有的未提交改动，不覆盖或回退无关内容。
- 证据先于完成宣称；证据不足时明确边界，不把 fixture、静态页面、文件存在或孤立测试当作真实链路完成。
- 达到预先说明的停止条件立即结束，不为完备度继续扩展范围。
- 两次有界等待都没有产生新证据时停止轮询，从最近证据点恢复、重新分派或报告阻塞，不把等待描述成进展。

拆分工作包、使用子 Agent、独立审查和运行 Harness 都是按风险、依赖和档位条件化的动作，不是每项任务的固定步骤。

## 5. 初始化与六个顶层文件

### 5.1 适用项目

长期维护或需要跨会话协作的产品，默认初始化以下六个顶层文件：

| 文件 | 唯一职责 |
| --- | --- |
| `AGENTS.md` | 极短的启动、路由和边界规则；指向其他事实源，不复制其内容。 |
| `PROJECT_STATUS.md` | 唯一的当前状态账本；记录当前目标、阶段、阻塞、下一步和证据，只替换当前事实，不追加历史。 |
| `SPEC.md` | 产品目标、非目标、行为、流程、状态和验收。 |
| `DESIGN.md` | 视觉语言、交互、响应式、可访问性、动效和视觉验收。 |
| `TECHNICAL.md` | 架构、数据、接口、安全、Harness、发布和恢复。 |
| `EVOLUTION.md` | 仅记录有证据且会改变未来行为的项目经验。 |

一次性脚本、微型库和已有成熟文档体系的项目，可以按需裁剪或不初始化，且应说明裁剪理由。初始化逐个检查目标文件；已有文件逐个跳过并保持字节不变，不合并、不覆盖。

### 5.2 启动与续接对账

`AGENTS.md` 只承担启动和路由，不成为第二份需求或流程文档。新会话必须对账：

1. Git 根目录、`HEAD`、`status` 和未提交 `diff`；若不是 Git 仓库，明确记录这一事实。
2. `PROJECT_STATUS.md` 的当前账本。
3. `SPEC.md`、`DESIGN.md`、`TECHNICAL.md`、`EVOLUTION.md` 中与当前任务有关的事实。

共享目录共享文件和 Git 状态，不共享旧聊天；旧聊天不能替代当前文件和工作区证据。

## 6. 视觉参考治理

治理对象是主 Agent、设计、开发、测试和验收的所有角色。

- 新项目的标准参考目录是 `design-references/`。现有项目若已有 `development-reference/` 等约定则沿用，不强制迁移。
- 只有在出现第一张被用户明确认可为参考的图片时才创建目录。探索稿不入库、不进入参考表。
- 用户明确说“作为参考”“按这个开发”等，才归档该张精确图片；同时更新 `DESIGN.md` 的参考表和可执行视觉规范，记录采用点、不得照搬的瑕疵，并同步 `PROJECT_STATUS.md`。
- 小瑕疵不自动重新生成、不自动触发付费调用。运行时使用的资产另行确认，不能因被归档为参考就视为已批准上线。
- 所有视觉任务先读 `DESIGN.md` 和有效参考图；不得依据 `final`、`v2`、新旧或文件名推断批准状态。

参考表至少能回答：图片是哪一张、批准用途是什么、采用了哪些可执行规则、哪些缺陷不能照搬。

## 7. 文档治理与经验回流

- 只在对应的当前事实发生变化时更新相应权威文档；产品、视觉、技术、协作和状态各司其职，避免复制同一规则。
- `PROJECT_STATUS.md` 只保留当前事实，不追加日志式历史。
- `EVOLUTION.md` 只有在存在可核查证据、明确适用条件且能改变未来行为时才维护；应合并、替换或删除过时条目，不机械追加。
- 项目经验先留在项目文档；跨项目适用性、非敏感性和证据充分后才形成全局 Skill 候选。全局修改、Git 提交、远程创建和推送均需用户确认。

## 8. Skill 结构与按需路由

保持最小结构：入口 `SKILL.md` 仅负责窄触发、三档选择、共享硬约束和资源路由；详细方法、Harness/发布、视觉参考治理和经验格式放在按需读取的 `references/`；重复且需要确定性的六文件初始化逻辑才进入脚本；模板、README 和测试各司其职。

入口可路由到三类工作：

- `Manage`：按三档选择探索、纵向切片、Bug 修复或发布门禁。
- `Init`：识别项目形态，按适用档案创建六文件或裁剪档案。
- `Evolve`：同步当前权威文档，或生成带证据和边界的经验候选。

Skill 只定义证据要求和门禁，不重造 Agent Harness，也不替项目选测试框架。

## 9. Harness、发布与授权门

证据层级保持：`H0` 格式/Lint/类型/局部构建，`H1` 单元与契约，`H2` 服务、数据库和适配器集成，`H3` 真实用户入口到服务与持久化，`H4` 经授权的真实外部服务，`H5` 生产产物、安装或部署、迁移、冒烟和回滚。

发布画像：

- `local`：正式安装包、隔离启动、用户数据、升级、重启、权限和卸载边界。
- `web`：生产构建、Staging、迁移、密钥、观测、灰度、冒烟和回滚。
- `dual`：共享适用的 H0–H4，并分别执行本地与 Web 的 H5。

严格档位的外部或付费调用必须先确认模型/服务、次数、尺寸或范围、输出位置和费用授权；还要验证未配置、认证失败、超时、取消和恢复。Git init、commit、远程创建和 push 是独立的发布授权门；Skill 可以在授权门前完成实现与本地验证，但不得越过发布门。

## 10. README 与验收

README 面向普通用户，必须用通俗语言说明平台兼容边界、通用使用方式、经核实的平台安装示例、适用与不适用场景、自然语言意图识别及边界、三档裁剪、六文件协作初始化、跨会话续接、开发协作、Bug 修复、测试验收、发布恢复、经验回流和视觉参考例子；不把内部术语或未发布能力写成承诺。

第一版验收必须证明：

1. 触发范围窄，普通问答、单文件简单修改和普通审查不会自动加载完整编排。
2. 三档能按风险给出不同动作、证据和停止条件。
3. 长期/跨会话项目默认得到六文件；裁剪项目和已有文件行为可验证且不覆盖。
4. 新会话对账、状态账本、文档职责和经验门禁无冲突。
5. 视觉参考只有用户明确批准后归档，所有角色使用同一批准基线，运行时资产仍需单独确认。
6. Skill、初始化脚本、README 和代表性行为验证通过；验证范围与风险相称。
7. 未经明确授权，不执行 Git 提交、远程创建、推送、发布或付费外部调用。
8. `SKILL.md` 和核心 references 不依赖特定 AI 编程产品；平台名称只用于 README 的兼容性说明、安装示例或测试历史。
